## How this works.

User documentation will be added to the big xml doc.  
Note that to use this software, at configure time:

*  Use the ```--enable-mvlc-stack-generator``` option when you run ```configure```
*  This requires the ```libyaml-cpp package``` (debian name) be installed in the system/container doing the build.  
```configure``` will check for the presence of that package using ```pkg-config```

### Background  

We want to support the Mesytec MVLC  controller, but make it easy for users of the VMUSBReadout
to transition to that controller.  Therefore mvclgenerate is a program that will
accept VMUSBReaodut daqconfig.tcl files, parse them and generate configuration files
that are acceptable for the fribdaq-readout program contributed to the
[Mesytec MVLC driver repository](https://github.com/flueke/mesytec-mvlc).

### Parsing the daqconfig.tcl

The simplest approach, and the one taken here was to provide a new
```CVMUSBReadoutList``` class that, rather than recording operations
in the form expected by the VMUSB controller, records them in the textual form
expected by the fribdaq-readout's .yaml configuration file.  Adding to this
a replacement class for ```CVMUSB``` that encapsulates a ```CVMUSBReadoutList```
and we can pass these to slightly modified exiting drivers imported from
```main/usb/vmusb/daqconfig``` to have them generate the initialization, end and
readout instructions in the proper form.


The class ```TCLConfigParser``` provides the data needed for this and a method to access it. It provides
the method ```addExtensions``` to add the commands that have been imported.   The derived class;
```MVLCConfigParser``` overrides that method to provide the Tcl commands that create, configure and
query the configuration of supported devices.

The main program ```generate.cpp``` instantiates a ```TCLConfigParser``` and 
asks it to interpret the input file.

### Generating  Output

Given that the trigger requirements of most (all?) experiments at the FRIB have been just for an input trigger
and a periodic scaler stack, and given that generating the trigger setup is not well documented, we start with a
template YAML configuration file that was generated by mdaq and exported to yaml, as well as slightly edited to ensure that all of the sections we might need to fill in are present.

This file is ```@srcdir@/triggeronly.yaml``` and gets installed in ```$DAQSHARE/mvlc/triggeronly.yaml```
The template file is set up with NIM1 as the event trigger for stack 1 and, in this initial release, 
a stack 2 triggered every two seconds (todo: figure out how to set this).  The file was also hand edited
to find the stack 0 (in the trigger module this is stack 1) start delay for the event stack and change the value of the VME write to the text ```STACKDELAY``` where it can be located and modified.

The class ```MVLCGenerator``` reads the template configuration file using libyaml-cpp which will be used to
edit the Yaml document..  

When asked to generate code, it 
uses the configuration (```TCLConfigParser```) to get the two stacks.

* If the event stack exists, the stack delay is modified in accordance with its ```-delay``` parameter.
If not, the delay is set to 0.  The readout, initialization, and shutdown are computed by the stack using the vmusb stand in classes described above and the Yaml is edited to plug the VME operations they generate.
* If the scaler stack exists, a similar process is used to fill in the Yaml for the initialization, read and shutdown sections of the YAML. 

Finally libyaml-cpp is ased to write the modified yaml document to the output file.

### Module notes:

The static nature of MVLC stacks means that some modules, which used to interact directly with the module
on initialization cannot do that any more and require some modifications.  Any module support that, in the VMUSBReadout was able to inform you that there is not a module of the type specified at the base address specified
cannot do so as this is an offline translator, running it does not require that an MVLC be connected to the host computer.

Other module specific differences:

#### C785

This module used to determine the module type (adc, tdc, qdc based on the model number register) and initialize as appropriate.  A new configuration option ```-type``` has been added with the legal values ```adc, qdc, tdc``` defaulting to ```adc```

if the 'adc' command is used for a tdc or qdc -type must be set.

Maybe it's possible to add more commands like tdc and qdc that will set the default -type?


#### mcppxxxxxx
 
*  For the VMUSB, if the -triggersource and -triggeroutput values where ```0x400```, the values of the trigger source
and trigger output in the module were used.  This is not possible with the fribdaq-readout framework, as interactive initialization is not supported.  Therefore, the raw value of these parameters is *always* used.
*  NSCLDAQ docs don't document the ```mdpp16qdc``` but it is there and implemented.
* The module configurations have a -printregisters option which, if true prints an annotated view of the device registers.   This is not supportable in the mvlc readout framework so it has been removed.

#### V1x90 

The CAEN multihit TDC's have two basic models, V1190 and V1290.  The V1290 has fewer channels but
higher resolution. In VMUSBReadout, the model can be read from the device and used to steer initialization and
readout list generation.  However in fribdaq-readout with the MVLC list handling is totally non-interactive.
Therefore the new option ```-model``` has been added with legal values:

*  ```v1190A```  - The module is a CAEN V1190 with 128 channels
*  ```V1190B```  - Th e module is a CAEN V1190 with 64 channels.
*  ```v1290A```  - The module is a CAEN v1290 with  32 channels.
*  ```v1290N```  - The module is a CAEN  v1290 with 16 channels

The default value for this is ```v1190A``` as this represents the vast majority of the modules at the FRIB.

#### SIS3316 digiitzer.

The support class for this device (```sis3316_class```) relies extensively oin interaction with the device at
initialization and cannot be supported in the translator environment.  A later version of ```fribdaq-readout```
may include built in modules like ```VMUSBReadout``` as Florian has added some stuff to his daq classes that 
might support this.  THerefore  stay tuned for later versions of that program and device support.
